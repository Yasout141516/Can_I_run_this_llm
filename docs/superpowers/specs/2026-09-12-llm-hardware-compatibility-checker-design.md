# LLM Hardware Compatibility Checker — Design

**Status:** approved design, pending implementation plan
**Date:** 2026-09-12
**Supersedes:** the open questions in [`handoff.md`](../../../handoff.md)

## 1. What this is

A static web app that answers one question: will this LLM run on my hardware?

The user supplies their hardware (looked up or entered by hand) and their inference
settings. The app sorts every tracked model into one of three buckets — **Run on GPU**,
**CPU Offloaded**, **Won't Run** — shows the memory breakdown behind each verdict, and
gives the command to actually run the ones that fit.

Prior art: runthisllm.com and llmrun.dev. Both are closed-box on their math. Ours is not:
every verdict shows its arithmetic.

## 2. Decisions

These resolve the open questions carried over from the handoff.

| Question | Decision |
|---|---|
| v1 cut line | Calculator **plus** benchmarks. Tokens/sec deferred to v1.1. |
| Frontend stack | Vite + React + TypeScript, static build |
| Data refresh | GitHub Actions cron runs ingestion, commits JSON, triggers redeploy |
| Model family list | Hand-edited `config/families.json` in the repo |
| Benchmark scores | Hand-curated `config/benchmarks.json`; no scraping (see §6) |
| Laptop data | Hand-curated seed list (~100–150 entries). No scraping, no external source. |
| "Run it" step | In v1, minimal — a per-engine command template |
| Quantisation sizing | Hybrid: real file size where published, formula fallback, provenance shown |
| Visual direction | Pixel/retro system, single committed theme (§9) |

Two constraints shape everything below: **no backend at runtime**, and **no network calls
from the app**. All data is static JSON bundled at build time.

## 3. Architecture

```
config/families.json        # hand-edited: tracked HF orgs/repos
config/benchmarks.json      # hand-edited: benchmark scores + sources
data/models.json            # generated by CI, committed
data/gpus.json              # hand-curated
data/laptops.json           # hand-curated
scripts/ingest/             # Node + TS, runs in GitHub Actions
src/lib/compat/             # the compatibility engine — pure, no I/O
src/                        # Vite + React app
tools/detect-specs/         # local spec-detection scripts (.ps1 / .sh)
.github/workflows/refresh-data.yml
```

The load-bearing boundary is `src/lib/compat/`. It is **pure TypeScript: no React, no
fetch, no file I/O**. Its entire public interface is:

```ts
evaluate(model: ModelSpec, hw: HardwareSpec, settings: Settings): Verdict
```

Everything uncertain about this project — the bits-per-weight table, the KV-cache formula,
per-engine offload rules, overhead margins — lives inside that one module. It is testable
without a browser, and the UI cannot grow a second copy of the math.

### Data flow

**Build time** (CI, every ~2 days): `config/families.json` → ingestion script → Hugging
Face for `config.json` (architecture) and repo file listings (real GGUF byte sizes) →
schema validation → `data/models.json` → commit → static redeploy.

The ingestion script **fails loudly rather than committing partial data**. A malformed or
missing upstream response aborts the run; it never writes a half-populated file. A wrong
VRAM number reaching users is worse than stale data.

**Runtime:** the app loads three static JSON files once, the user sets hardware and
settings, and `evaluate()` runs across all models on every change. It is arithmetic over a
few hundred records — fast enough that there is no submit button and no memoisation in v1.
The app works offline once loaded.

## 4. Data model

### ModelSpec

```ts
interface ModelSpec {
  id: string;              // "meta-llama/Llama-3.1-8B-Instruct"
  family: string;          // "Llama 3.1" — groups entries from families.json
  displayName: string;
  params: { total: number; active: number | null };
  arch: {
    numLayers: number;
    numKvHeads: number;
    headDim: number;
    maxContext: number;
  };
  quants: QuantOption[];
  benchmarks: Record<BenchmarkId, number | null>;
  categories: Category[];
  source: { hfRepo: string; ggufRepo?: string; fetchedAt: string };
}
```

`params.active` is `null` for dense models and a number for mixture-of-experts. It is
modelled as nullable rather than defaulting to `total` because the two values feed
*different* formulas, and conflating them is the single most likely way to get an MoE
verdict wrong:

- `total` drives **memory** — every expert must be resident
- `active` drives **speed** only

`numKvHeads` is tracked separately from attention heads because grouped-query attention
models often have 8 KV heads against 64 query heads. Using the wrong one inflates the KV
cache eightfold and makes long-context verdicts meaningless.

### QuantOption

```ts
interface QuantOption {
  id: string;                             // "Q4_K_M" | "AWQ-4bit" | "FP16"
  format: "gguf" | "awq" | "gptq" | "fp8" | "safetensors";
  sizeBytes: number;
  sizeSource: "measured" | "estimated";
  fileName?: string;                      // present iff measured
}
```

`sizeSource` implements the hybrid decision and is surfaced in the UI as a badge. Being
honest about which numbers are estimates protects trust precisely where it matters — a
borderline "fits" that turns out not to.

`format` gates engine compatibility. Selecting vLLM removes GGUF options from the
quantisation control, rather than allowing a configuration that cannot exist.

### HardwareSpec and Settings

```ts
interface HardwareSpec {
  kind: "discrete-gpu" | "apple-silicon" | "cpu-only";
  vramBytes: number;
  ramBytes: number;
  ramType?: RamType;
  memBandwidthGBs?: number;   // ingested in v1, consumed in v1.1
}

interface Settings {
  engine: EngineId;
  contextLength: number;
  kvPrecision: "fp16" | "q8" | "q4";
  quantId: string | "auto";
}
```

The supporting unions, enumerated so ingestion and UI cannot drift apart:

```ts
type EngineId     = "ollama" | "llamacpp" | "koboldcpp" | "vllm" | "tgi" | "sglang";
type QuantFormat  = "gguf" | "awq" | "gptq" | "fp8" | "safetensors";
type RamType      = "DDR4" | "DDR5" | "LPDDR4X" | "LPDDR5" | "LPDDR5X" | "unified";
type Category     = "chat" | "code" | "reasoning" | "vision" | "embedding"
                  | "medical" | "finance" | "legal";
type BenchmarkId  = "mmlu" | "mmlu_pro" | "gpqa" | "humaneval" | "math"
                  | "ifeval" | "swe_bench";
```

`Category` and `BenchmarkId` are the v1 sets. Both are additive — a new benchmark is a new
union member plus a column, with `null` meaning "not reported", which is deliberately
distinct from a score of zero.

`kind` is a discriminated variant because Apple Silicon is not "a GPU with a large number".
Unified memory means there is no VRAM/RAM boundary to spill across, and the allocatable
ceiling is a fraction of the shared pool. Making it a variant forces `evaluate()` to branch
explicitly instead of letting a Mac fall through desktop-GPU logic.

`memBandwidthGBs` is ingested in v1 but unused. Collecting it now costs nothing and avoids
re-running ingestion when tokens/sec lands in v1.1.

### Lookup tables

`GpuEntry` and `LaptopEntry` resolve *into* a `HardwareSpec`. The rule that satisfies the
manual-override requirement: **a lookup writes into form state and then has no further
authority.** Form state is the single source of truth. Overriding a prefilled value is just
typing — there is no locked state to unwind, and no way for a laptop preset to contradict
what the user typed.

`data/models.json` carries a `schemaVersion`. If the app loads data it does not understand,
it says so loudly rather than reading a renamed field as `undefined` and reporting 0 GB.

## 5. Compatibility engine

### Engines are data

```ts
interface EngineProfile {
  id: EngineId;
  formats: QuantFormat[];
  supportsCpuOffload: boolean;
  preReservesKvPool: boolean;
  memoryUtilization?: number;
  overhead: { baseBytes: number; perContextBytes: number };
  runCommand(model, quant, settings, verdict): string;
}
```

| Engine | Formats | CPU offload | Pre-reserves KV pool |
|---|---|---|---|
| Ollama | gguf | yes | no |
| llama.cpp | gguf | yes | no |
| KoboldCpp | gguf | yes | no |
| vLLM | awq, gptq, fp8, safetensors | no | yes (0.9) |
| TGI | awq, gptq, safetensors | no | no |
| SGLang | awq, gptq, fp8, safetensors | no | yes (0.9) |

Adding an engine is adding a row. `runCommand` lives beside the rules it depends on, which
is what makes "Run it" nearly free rather than a second subsystem.

### Weights

```
weightBytes = quant.sizeSource === "measured"
            ? quant.sizeBytes
            : params.total × bitsPerWeight(quant.id) / 8
```

GGUF k-quants mix precision per block, so these are approximations, not exact values:

| Quant | bpw | Quant | bpw |
|---|---|---|---|
| FP16 / BF16 | 16 | Q4_K_M | 4.8 |
| Q8_0 | 8.5 | Q4_0 | 4.5 |
| Q6_K | 6.6 | Q3_K_M | 3.9 |
| Q5_K_M | 5.7 | Q2_K | 2.6 |

Non-GGUF formats use a separate table (AWQ-4bit ≈ 4.25, GPTQ-4bit ≈ 4.25, GPTQ-8bit ≈ 8.25,
FP8 / INT8 = 8), because they are not k-quants and sharing one table would silently
misprice them.

### KV cache

```
kvCacheBytes = 2 × numLayers × numKvHeads × headDim × contextLength × bytesPerElement
```

The leading `2` is K and V. `bytesPerElement` is fp16 = 2, q8 = 1, q4 = 0.5.

### Overhead and usable memory

Overhead — CUDA context, activation and compute buffers — is the honest fudge factor in
this design. It lives as **named per-engine constants in one table**, never as magic numbers
inside the math, because it is the term that will actually be tuned against real-world
reports.

Usable system RAM is not all system RAM. The OS needs headroom:

```
ramReserve = max(ramBytes × 0.15, 2 GB)
usableRam  = ramBytes − ramReserve
```

Treating 32 GB as 32 GB is how you promise someone a model that thrashes their machine.

Usable VRAM depends on `kind`, and is defined once so the categorisation rules and the
layer-split formula cannot disagree:

```
usableVram = kind === "apple-silicon" ? pool × APPLE_WIRED_FRACTION  // 0.75
           : kind === "cpu-only"      ? 0
           :                            vramBytes
```

Every rule below reads `usableVram`, never `vramBytes` directly.

### Categorisation

Guard clauses first:

1. `contextLength > model.arch.maxContext` → **Won't Run**, `limitingFactor: "context"`
2. no quant whose `format` is in `engine.formats` → **Won't Run**, `limitingFactor: "format"`

Then, with `required = weightBytes + kvCacheBytes + overheadBytes`:

**Discrete GPU.** `required ≤ usableVram` → Run on GPU. Otherwise, if
`engine.supportsCpuOffload` and `required ≤ usableVram + usableRam` → CPU Offloaded.
Otherwise Won't Run.

**Apple Silicon.** One pool, no boundary to spill across, so system RAM is never added —
`usableRam` does not apply. `required ≤ usableVram` → Run on GPU; `≤ pool ×
APPLE_SOFT_CEILING` (0.90) with offload support → CPU Offloaded; otherwise Won't Run. Both
fractions are named constants because the wired-memory limit is user-adjustable on macOS.

**vLLM and SGLang** take a different path, because they pre-reserve
`memoryUtilization × VRAM` up front and carve KV out of that budget. The test is not "does
the sum fit" but "do weights fit inside the reserved pool, with room left for KV blocks".
Same inputs, genuinely different arithmetic — which is why `preReservesKvPool` is a flag
rather than a comment.

### Verdict

```ts
interface Verdict {
  status: "run-on-gpu" | "cpu-offloaded" | "wont-run";
  breakdown: { weightsBytes; kvCacheBytes; overheadBytes; totalBytes };
  confidence: "measured" | "estimated";
  gpuLayers?: number;
  limitingFactor?: "vram" | "ram" | "context" | "format";
  notes: string[];
}
```

Returning a breakdown rather than a boolean pays twice. The UI can explain *why* — "your
VRAM is fine, your context length is not" beats a red X. And `gpuLayers`:

```
bytesPerLayer = weightBytes / numLayers
gpuLayers     = clamp(floor((usableVram − kvCacheBytes − overheadBytes) / bytesPerLayer),
                      0, numLayers)
```

is simultaneously the offload verdict **and** the exact `--n-gpu-layers` value the Run It
command needs. Two features, one calculation.

`bytesPerLayer` divides weights evenly across layers, which ignores embeddings and the
output head — those are not per-layer tensors. This is a deliberate, documented
approximation: it is close enough for a layer count, and the golden-file tests pin how far
off it is allowed to drift.

### How we know it is right

Golden-file tests over `src/lib/compat/`, written **before** the implementation. Anchors:

- the handoff's own reference point — 7B ≈ 14 GB at FP16, ≈ 4 GB at Q4_K_M
- published GGUF file sizes for tracked models
- community reports of what fits in 8 / 12 / 16 / 24 GB

When a constant is tuned, the tests show what else moved. This is the difference between a
calculator and a guess.

## 6. Ingestion and CI

`scripts/ingest/` reads `config/families.json`, and for each tracked family:

1. fetches `config.json` for `num_hidden_layers`, `num_key_value_heads`, `head_dim`,
   `max_position_embeddings`
2. lists repo files to capture real GGUF byte sizes where published
3. fills remaining quantisation levels from the bpw formula, marked `estimated`
4. merges in benchmark scores and category tags from `config/benchmarks.json`
5. validates the whole output against the schema
6. writes `data/models.json` only if validation passes

Step 4 needs saying plainly: **benchmark scores are hand-maintained, not fetched.** There is
no equivalent of `config.json` for evaluation results — scores live in model cards, papers
and leaderboards, in inconsistent formats, produced under inconsistent eval harnesses.
Scraping them would produce a table that silently compares numbers measured different ways,
which is worse than having fewer numbers. So `config/benchmarks.json` is curated alongside
`config/families.json`, each entry recording where its score came from. A tracked model with
no scores yet renders `null`, not a blank.

`.github/workflows/refresh-data.yml` runs this on a schedule, and commits only when the
output differs. Every data change is therefore a reviewable diff in git history — a bad
upstream value is visible and revertable, not silently live.

## 7. Local spec detection

Browser APIs for VRAM and RAM were rejected as unreliable. Instead `tools/detect-specs/`
holds a small script the user runs on their own machine:

- GPU model and VRAM — `nvidia-smi`, `rocm-smi`, `system_profiler`
- RAM size, type, speed — `wmic memorychip`, `system_profiler SPMemoryDataType`,
  `/proc/meminfo`
- CPU model

On Windows, prefer `nvidia-smi` over WMI: WMI's `AdapterRAM` is a 32-bit field and
misreports VRAM above 4 GB.

Output is compact JSON the user pastes into `/detect` to prefill the form. Chosen over a
localhost bridge to avoid both the added complexity and the antivirus-flag risk of a script
that opens a port.

## 8. UI surfaces

**`/` — the calculator.** Hardware panel (device lookup, laptop lookup, manual entry,
engine, context, KV precision, quantisation); stat tiles counting Run / Offload / Won't
Run; category chips, search, sort, cards-or-table toggle; the model list. Every input change
re-runs the evaluation — no submit button.

**`/model/:id` — the report.** Memory breakdown as a stacked bar drawn to the VRAM scale,
the verdict with its limiting factor, benchmark scores, and the Run It command with a copy
button.

**`/benchmarks`** — sortable, filterable scores table, a column per benchmark.

**`/detect`** — download the detection script, paste its output back to prefill.

**The coach-mark tour** walks the hardware panel on first visit (dismissible, remembered in
`localStorage`), and every `?` icon reopens its tip on demand. Tips are data in a single
file, not copy embedded in components — one content source, two entry points. This earns
its place because someone who does not know what KV precision *is* cannot fill the form.

## 9. Visual system

Pixel/retro, a single deliberately committed theme. Built and reviewed at
[`docs/design/style-reference.html`](../../design/style-reference.html).

| Token | Value |
|---|---|
| Ground | `#55547E` indigo, two faint radial washes |
| Card | `#FCF9EC` cream |
| Ink | `#141046` near-black navy |
| Accent | `linear-gradient(103deg, #7C3AED, #2F6FED 58%, #2DD4BF)` |
| Status | Run `#2FB673` · Offload `#F0A429` · Won't `#E25548` |
| Structure | 3px borders · 14px radius · `6px 6px 0` shadow, no blur |
| Type | Archivo Black (display) · IBM Plex Sans (body) · IBM Plex Mono (labels, numbers) |

Rules that carry the identity:

- **Status is never colour alone.** Every verdict carries a glyph, a word, and a colour. The
  entire output of this app is a three-way status; colour-only encoding would fail
  colour-blind users completely.
- **Status colour is not the accent.** The gradient is for actions and chart marks; semantic
  colour is reserved for verdicts.
- **Buttons press with `steps(2)` timing**, translating 4px into their own shadow. An eased
  transition quietly undoes the pixel feel.
- **Single theme, painted explicitly.** No light variant — the indigo world is the product
  identity. Every colour is set from a token so the page holds on any host background.

One known constraint: Archivo Black ships a single weight, so there is no lighter cut for
mid-level headings. `/benchmarks` has many column headers and could read as shouty; column
headers there use IBM Plex Mono rather than the display face.

## 10. Testing

In priority order:

1. **Golden-file tests on `src/lib/compat/`**, written before the implementation. This is
   where correctness lives.
2. **Schema validation over `data/*.json`** — doubles as the CI gate that stops the cron job
   committing malformed data.
3. **Component tests** for form-state-is-truth: a laptop prefill must remain overridable.

No end-to-end tests in v1.

## 11. Out of scope for v1

- Tokens/sec estimates (v1.1 — `memBandwidthGBs` is collected now to make it cheap)
- Scraped laptop data (hand-curated seed list only)
- Full Hugging Face auto-discovery (curated families only)
- User-added custom models in browser storage
- Multi-GPU and tensor-parallel configurations
- Training or fine-tuning memory estimates — this app answers inference only

## 12. Risks

**Overhead constants are empirical.** They are the least certain numbers in the engine.
Mitigation: one named table, golden-file tests that pin the effect of changes.

**Estimated sizes cluster on new models** — the ones users most want to check are the least
likely to have published GGUF files. Mitigation: the provenance badge makes the uncertainty
visible rather than hidden.

**Hand-curated laptop coverage will have gaps.** Accepted: because manual override is always
available, a miss costs the user seconds, not the answer.

**Upstream `config.json` field names vary** across architectures (`head_dim` is sometimes
absent and must be derived from `hidden_size / num_attention_heads`). Mitigation: ingestion
validates and fails loudly rather than defaulting.
